## Speed and machine notes

AMR streams through one long-lived ffmpeg per bitrate per loader worker (loader 829–1036 s/s); 4 workers for S2; validation cached on the GPU; closed phase on the GPU (`add_model.py`, `VA_DEVICE=cuda`, identical to CPU); `torch.compile` and HIP graph capture parked (no Triton on ROCm under Windows; capture aborts in hipBLASLt); priority opt-in (`VA_PRIORITY`), no measurable gain; under CPU load S2 loses 15–36 %, so keep measures off the CPU during training. Open: a batched GPU eval suite for the paired measures and the probe (closed phase done); profiling the training step needs ablation timing, since the ROCm profiler's GPU times are unreliable here. Machine notes: CPU boost on; CPPC core order 7, 8, 5, 4, 1, 6, 3, 2, then 11, 12, 13, 15, 10, 16, 9, 14 (HWiNFO numbering from 1); the main training thread runs on cores 6–7 (Windows numbering) and GPU use follows it.

## Training recipe experiments (next item 3)

Each runs on S2 and train_v2 against three same-seed baselines. The cheap screen is synthetic validation loss and F1–F3 error; anything that passes then gets the subset real-voice measures with 2–3 seeds. Optimiser and schedule choices tend to carry over to larger models. The best learning rate does not: it changes with model width.

| Experiment | Why |
|---|---|
| Shorter warmup (about 250–300 steps) | 1000 steps is 29 % of a 3.5k run |
| Larger batch (64), learning rate and steps adjusted | halves the per-step CPU cost per second of audio for small models |
| Learning-rate sweep (×0.5, ×2, ×3) | 1e-3 has never been tuned |
| Decay length about 20 % of the run (now 43 %) | the WSD literature finds about 20 % enough, so runs get cheaper |
| Muon for 2-D weights (GRU, linear), AdamW for the rest | built into torch 2.13; strong results on transformers, and relevant to the Conformer |
| Adan / AdanW | gains reported in vision and NLP papers; three betas to tune; not in torch, on PyPI |
| Schedule-free AdamW, retested with seeds | D-018 was a single-run comparison: better F1, worse f0 RPA |
| Cosine instead of linear warmup | usually small once the warmup length is right |
| `torch.compile`, channels-last | speed only; uncertain on ROCm under Windows |

- **Device processing: automatic gain control** (Hannah, 2026-10-24). The channel model's level is one static gain per clip (`gain_db`) followed by clipping and the codec; nearly every phone, laptop and video-call path also runs AGC before its encoder, so the consented outcome recordings will mostly have been through one. Model it as one AGC on the **final mix** (room → noise / scene mix → AGC → clipping → codec, behind a channel-config switch, off by default), since a real AGC derives its gain from whatever reaches the microphone: on a clean recording it evens out the speaker's own level; with a scene, a loud event (a motorcycle passing) makes it duck the voice with it, and the noise floor pumps back up in the gaps. It belongs to the channel model, not to `random-cafe` (it is the device, not the scene); `random-cafe` supplies the events. Parameters drawn per clip: attack (about 1–20 ms), release (50 ms – 2 s), target level, maximum gain (up to about 20–30 dB), ratio and knee, plus a slow adaptive-digital-gain mode (WebRTC AGC2-like). Cheap: an attack/release envelope follower on 1 ms blocks, interpolated. Labels are level-independent. Where it could hurt: gain moving within the VQT's long low-frequency windows (low bins see an averaged gain, high bins the current one: a transient tilt change in the F1 region), fast attack modulating within a glottal period at high f0 (sidebands, harmonics broadened, so bandwidths), and pumping noise between words (voicing). **Two steps**: (1) an evaluation-only stress test, no training: the dev gold sets through a few AGC presets (slow digital gain; fast phone compressor; either ducking under a `random-cafe` scene), teacher v3 scored as paired differences against the unprocessed audio (F1 bias, bandwidths, voicing); (2) only if that shows harm, a pre-registered augmentation arm (AGC with probability p, nothing else changed). The stress set stays as a robustness check either way.
- **Device processing: noise, echo and reverberation suppression** (Hannah, 2026-10-24). Probably more destructive than AGC, since it reshapes the spectrum rather than scaling it: spectral-subtraction / Wiener / neural noise suppressors notch and smear harmonics and can eat weak high formants (F3 / F4 observability, D-027); residual-echo suppression (the non-linear stage after acoustic echo cancellation) gates and attenuates onsets and tails, and in an acoustically reflective room it treats the voice's own reverberant tail as echo; dereverberation does the same deliberately. Many devices **beamform** with two or more microphones first, which needs the spatial scene: `random-cafe` / pyroomacoustics rendering the voice and each noise source to a small microphone array (phone, laptop, headset geometries) rather than one microphone, then the beamformer, then single-channel suppression, AGC and the codec. Real devices' processing is proprietary, so use open stand-ins as proxies, licence and build to check before use (candidates: WebRTC's audio processing module (BSD: AEC3, noise suppression, AGC2), SpeexDSP's preprocessor (BSD), RNNoise (BSD), and a classical delay-and-sum / MVDR beamformer written here). Same two steps as AGC: an evaluation-only stress test first (dev gold sets through each processor, with and without a scene and a reflective room; teacher v3 paired against the unprocessed audio), then, only on demonstrated harm, a pre-registered augmentation arm. Order with AGC: beamformer → echo / noise suppression → AGC → codec, as in typical voice-processing pipelines.
